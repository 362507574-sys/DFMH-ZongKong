# 增长机会分析

## 用户版成果输出

专业交付统一规则：一级标题必须使用固定编号并去掉“技能”后缀；二级标题使用“1.1”式固定编号；三级标题依次使用“核心判断、深度分析、依据与边界、落地建议”并使用“1.1.1”式固定编号；四级标题继续拆分为“关键变量、推导逻辑、已知事实、待验证信息、执行动作、验收指标、风险与停止条件”并使用“1.1.1.1”式固定编号。每个业务分析子项至少500个有效字符，必须形成该岗位专属的专业推导，事实、推断与信息缺口分开，必要说明使用括号标注；禁止统一模板扩写、重复套话或用篇幅冒充分析深度。

唯一目录事实源为 `control-center/registries/organization-output-standard.json`。本技能在用户版组织 Word 中固定使用一级章节“增长机会分析”，并严格按以下顺序输出：

1. 市场趋势
2. 用户需求
3. 行业机会
4. 增长空间

每个栏目必须结合当前地域、品类、企业能力和真实信号给出判断；公开可核验内容必须先检索，互动不能冒充购买。仍缺少企业内部不可替代事实时写明：`信息不足，暂时无法形成可靠分析。当前缺少：<具体信息>。` 机会评分、证据等级和实验细节融入对应栏目，不新增用户版目录。

## 基础运行闭环（完整链路强制）

当控制中心选择 `growth-basic-pipeline`，或任务需要中断恢复、修改闭环、精确版本交接时，必须把 `organizations/ai-growth-strategist/scripts/growth_basic_run_manager.mjs` 作为唯一基础运行入口；不得用零散调用 `growth_run_store.mjs`、规划器或候选校验器代替运行管理。增长机会的十二步分析与 v2 校验仍照常执行，校验通过后再把候选载荷提交给基础运行器。

固定顺序：

1. 使用可信的 `enterpriseId`、`businessProjectId`、`taskId`、`runId` 与用户原始大白话目标调用 `createBasicGrowthRunManager({ projectRoot })` 后执行 `start(...)`。
2. 同一身份与同一原始目标重复执行 `start(...)` 时恢复原运行；查询进度使用 `status(...)`，不得新建运行或重跑已完成成果。
3. 本技能完成内部分析、调试和 v2 候选校验后，调用 `submitStage(...)`，其中 `skillId` 固定为 `growth-opportunity-analysis`；基础运行器写入不可变成果版本。若同一运行的 `nextSkillId` 为 `competitive-benchmark-analysis`，就在原运行内继续；运行器会把机会成果的精确版本、相对路径与 SHA-256 自动写进下游成果的 `upstreamArtifacts`，不得靠模糊引用，也不得把同组织技能流转伪装成跨组织交接。
4. 用户要求修改已交付机会时，在审核态调用 `reviseStage(...)` 并写明原因；必须产生新版本，保留旧版本，并使其后的竞争对标与内容客户增长成果失效后重做，禁止原地覆盖。
5. 只有交给其他组织时才调用 `createHandoff(...)`；只交接运行器返回的精确 `artifactId@version`、相对路径与 SHA-256，不引用 `current` 或“最新文件”，也不得把目标组织写成 AI增长战略官自身。
6. 本次运行选定的全部技能都完成且用户最终验收后才调用 `accept(...)`；不得把内部完成自动解释为验收。中断后再次调用 `status(...)` 或同一 `start(...)`，由运行器恢复未完成的成果或验收事务。

基础运行器只管理运行、版本、恢复与交接，不替代本 Skill 的证据质量、十二步作战链、v2 契约校验和安全门禁。任何发布、投放、客户联系、价格或退款规则修改仍保持阻断。

基础三层版的内部状态只使用 `running_internal → reviewing → completed`；下方含 `awaiting_approval / running_approved` 的完整状态机用于未来经批准的外部动作，不得据此虚构基础运行器已有批准接口。

## 核心原则

只把可追溯证据支持的机会排进优先级。把事实、推断、假设和未知分开记录，用“机会吸引力 × 证据可信度”决定先实验、先补证、暂缓或停止。

保持 AI增长战略官为唯一主责。增长定位只决定优先人群、场景、渠道与实验顺序，不改写企业战略、品牌核心定位、价格或成交规则。

## 输入

读取并锁定：

- 控制中心提供的 `enterpriseId`、`businessProjectId`、`taskId`、`runId` 和组织归属；
- 企业目标、产品或服务、地域、时间、预算、人员、渠道、当前基线和风险限制；
- 飞书知识前置检索凭证；`no_hit` 或 `degraded` 仍继续，但降低结论强度；
- 企业事实、客户原话、行为数据、必要公开来源及来源版本；
- 已确认的企业分析、战略、商业模式、品牌和成交边界，使用精确 `artifactId@version` 与 SHA-256，不读取模糊的“最新文件”。

缺少不可替代事实时形成受限候选和补证实验，不补造市场规模、趋势、需求、收益或因果结论。

## 执行

1. 执行前置检索，读取 `organizations/ai-growth-strategist/workflows/GROWTH_OPPORTUNITY_ANALYSIS.md`。
2. 用 `growth_opportunity_planner.mjs` 生成十二步计划，并写入当前企业项目舱。
3. 把输入写入证据账本，逐条保存类型、来源、时间、适用范围、版本、SHA-256、可信度与冲突关系。
4. 依次完成四条支线：
   - `market-trends`：区分长期趋势、短期热点和噪声；
   - `user-demand`：区分表达、行为、付费信号和推断；
   - `industry-opportunity`：分析供需、替代、竞争、进入条件和时间窗口；
   - `enterprise-growth-space`：分析获客、激活、培育、询盘、成交和复购断点。
5. 生成机会池。每个机会绑定事实证据、`counterEvidenceRefs`、未知和适用边界。
6. 计算 0—100 吸引力：需求强度25%、企业适配20%、可触达15%、潜在价值15%、时间窗口10%、竞争与执行15%。
7. 评定 A—D 可信度。只统计企业事实、客户原话、行为数据、可靠公开来源和知识来源；`inference / hypothesis / unknown` 不计入证据类型数。A 至少包含三类可靠证据和企业行为数据；B 至少包含两类可靠证据；存在未解决冲突时不得评为 A 或 B；证据不足时使用 C 或 D。
8. 形成优先级地图：
   - 吸引力 `>=70` 且可信度 A/B：`priority_experiment`；
   - 吸引力 `>=70` 且可信度 C/D：`evidence_first`；
   - 吸引力 `<50` 且可信度 C/D：`stop`；
   - 其余 `50—69`，以及 `<50` 但可信度 A/B：`hold`。
9. 为候选机会建立最小实验，写明对象、对照、样本、基线、主/辅/风险指标、目标、期限、成本、停止条件、回收方法和复盘时间。
10. 用 `growth_opportunity_debugger.mjs` 检查无来源规模、互动冒充购买、相关性冒充因果、评分敏感性、不可测指标、缺停止条件和组织越界。
11. 生成 v2 JSON，使用标准输入运行 `validate_candidate.mjs`。保留 v1 兼容，不把 v1 静默改写成 v2。
12. 基础三层版内部分析完成后进入 `reviewing`。若后续请求发布、投放、联系客户或其他外部动作，只把该动作标记为 `awaiting_approval` 并阻断，不把基础运行主状态伪装成已获批准；未经用户批准，不发布内容、不投放、不联系客户、不改价格、不作品牌或成交承诺、不写外部系统。

## 输出与验收

输出精确版本的 `growth-opportunity-brief` 候选，包含：

- 增长问题诊断、四支线结果和证据账本；
- 机会池、反证、未知、吸引力与可信度地图；
- 优先人群、场景、渠道和实验顺序；
- 有界实验、调试报告、协作请求和复盘规则；
- 供下游使用的固定版本交接信息。

候选只能保存在当前项目舱的组织工作区，不得直接写 `shared-artifacts/` 或根级 `outputs/`。下游必须读取控制中心发布的精确版本。

验收要求：

- 事实、推断、假设和未知分离；
- 四支线完整，外部事实带来源、时间、适用范围、版本和指纹；
- 每个机会有事实证据、反证和未知；
- 吸引力可复算，可信度符合证据门槛；
- 每个实验可测量、有期限、成本和停止条件；
- 保证增长、虚构规模、自动外部动作和组织越界为零；
- v2 候选通过 `validate_candidate.mjs`，v1 演示继续通过。

## 调试、异常与恢复

十二步业务作战链描述分析工作，以下共享运行状态机描述整次运行阶段：

```text
intake → planning → ready → running_internal
→ awaiting_approval → running_approved → reviewing → completed
```

共享异常运行状态严格为：

```text
retrying / missing_input / evidence_conflict / boundary_blocked
/ cost_stopped / paused / failed
```

取消或归档属于项目生命周期控制，不写成未定义运行状态，也不得自动恢复。

每次运行保存完整运行级 debug bundle：目标、输入版本、证据清单、作战计划、步骤时间线、工具状态、错误分类、重试记录、修复动作、候选输出、门禁结果、指标快照、复盘结论、可重放输入。

候选内 `debugReport` 只是摘要，固定包含 `status`、`diagnostics`、`remainingUnknowns`；每条诊断包含 `code`、`severity`、`field`、`explanation`、`recoveryAction`。任一 `severity=blocking` 时摘要 `status=blocked`；这里的 `blocked` 不是共享运行状态。

v2 CLI 必须由调用方传入可信的预期企业、项目、任务、运行身份与 `projectRoot`，不得从候选自证。`matched / degraded / no_hit` 的知识凭证都必须位于当前项目运行目录，是真实非链接文件且 SHA-256 匹配。

- 知识检索 `no_hit` 或 `degraded`：保存凭证，继续受限分析；
- 来源失效或冲突：保留冲突并降低可信度，不选择有利结论；
- 临时工具、网络或文件占用：最多重试两次；
- 候选契约错误：修正同一候选，最多三轮；
- 中断：从最后已验证步骤恢复，不重跑全部前序动作；
- 同一根因连续三轮仍失败：进入 `failed`，保存最后错误、时间线和可重放输入；
- 缺少关键事实：进入 `missing_input` 或补证实验；
- 付费、权限、安全、外部发布或组织越界：不重试，进入审批或阻断状态。

取消或归档项目不得自动恢复。

## 组织边界

- 改变企业战略、商业模式或资源总盘：请求 AI掌舵官；
- 改变品牌核心定位或正式品牌承诺：请求 AI品牌官；
- 进入报价、异议、成交、价格、购买或续费决策：请求 AI成交官；
- 改变岗位、训练、绩效或组织体系：请求 AI组织官。

协作只补充边界输入，不改变 AI增长战略官主责。

## 示例

用户：“自助测算页有620次有效访问，完整填写率31%，随后有17次企业主动预约；同期普通产品页有410次有效访问、预约6次，但两类页面没有用户级归因。下一阶段先验证什么？”

正确做法：把访问、填写和主动预约作为聚合行为事实，把页面访问导致预约的因果关系标为未知；四支线均给出结论或受限状态；形成带反证的机会卡；用聚合页面版本设计30天以内实验；请求 AI成交官确认“主动预约”交接定义，但不作成交承诺。

结构模板见 `templates/growth-opportunity-analysis.v2.json`，通过示例见 `examples/growth-opportunity-analysis.v2.demo.json`。
