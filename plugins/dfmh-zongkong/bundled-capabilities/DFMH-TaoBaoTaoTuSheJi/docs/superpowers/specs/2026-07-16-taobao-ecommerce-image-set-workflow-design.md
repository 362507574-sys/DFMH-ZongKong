# 淘宝电商套图链路设计规范

- 日期：2026-07-16
- 状态：设计已获用户批准，等待书面复核后制定实施计划
- 适用线程：主流程线程、测试线程；正式生产线程仅在链路升级为正式 Skill 后调用
- 推荐方案：结构化半自动硬门禁

## 一、目标

建立一条可重复运行、可中断恢复、可追踪版本、能够验证产品真实性与整套视觉一致性的淘宝电商套图生产链路。

链路保留现有操作习惯：默认使用 QQ 浏览器中的 ChatGPT 网页生图；首次生成时上传产品原图，后续正常情况下按顺序只发送逐张生图提示词。项目文件负责管理素材、卖点、提示词、图片、版本、验收证据和正式成果。

本设计先形成试运行工作流。至少完成一项真实产品套图和一次修改闭环，并通过基线测试、异常测试与复测后，才封装正式 Skill。

## 二、范围与分流

### 2.1 本链路覆盖

- 淘宝首图组（首页图）；
- 淘宝详情页图；
- 同时包含淘宝首图组和详情页图的完整电商套图；
- 产品卖点提炼、提示词规划、网页生图、归档、逐张验收、整套验收和正式交付。

### 2.2 本链路不覆盖

- 普通产品宣传海报；
- 节日、活动和品牌宣传海报；
- 与淘宝电商套图无关的单张视觉；
- 未经授权的第三方素材上传；
- 未经用户批准的付费接口或第三方服务。

普通宣传海报继续使用 `skills/creating-promotional-posters/SKILL.md`，不得用该 Skill 代替淘宝电商套图链路。

### 2.3 模糊需求分流

当需求只写“产品图”“淘宝图”或“电商图”时，先确认属于以下哪一种：

1. 普通产品宣传海报；
2. 淘宝首图组（首页图）；
3. 淘宝详情页图；
4. 完整淘宝电商套图。

关键范围未确认前不得进入卖点提炼或生图。

## 三、术语

- **淘宝首图组（首页图）**：淘宝商品前台展示区域使用的一组 1:1 图片，每张只表达一个核心卖点。
- **首个实际队列项**：按任务范围确定的第一张待生成图片；`home/full=H01`，`detail=D01`，同时作为本任务视觉风格锚点。
- **详情页图**：1080×2340 的单屏长图，按浏览顺序组成 8–12 屏详情页。
- **卖点证据**：产品图片可见事实、用户明确提供的产品事实，或正式产品资料能够证明的信息。
- **产品漂移**：生成图中的产品颜色、比例、结构、配件、材质、品牌或关键细节偏离参考产品。
- **纯净生图提示词**：能够直接提交给 ChatGPT 生图、且不包含任务分析与内部备注的完整提示词。
- **逐张验收**：每张图片生成后的独立质量检查。
- **整套验收**：全部单图通过后，对统一性、变化性、节奏与完整性的整体检查。

## 四、方案比较与决策

### 4.1 方案 A：纯聊天人工链路

优点是操作快；缺点是提示词、图片、版本和验收结果容易错配，无法稳定跨线程复用。

### 4.2 方案 B：结构化半自动硬门禁

保留 QQ 浏览器和 ChatGPT 网页生图，通过任务清单、独立提示词文件、版本编号、状态门禁、归档和验收保证可靠性。

### 4.3 方案 C：全自动接口生图

自动化程度高，但会改变现有工具链，涉及接口配置、费用、授权和新的输出稳定性风险。

### 4.4 采用方案

采用方案 B。方案 A 不能满足可追踪和可验证要求；方案 C 当前超出既定工具、费用和授权边界。

## 五、核心原则

1. 未确认需求范围，不提炼卖点。
2. 未确认卖点，不生成首图或详情页提示词。
3. 未确认整套提示词，不调用生图工具。
4. 未确认首个实际队列项的风格锚点，不连续生成余下套图。
5. 当前图片未通过逐张验收，不发送下一条提示词。
6. 单图全部通过后，必须再执行整套一致性验收。
7. 未经用户最终验收，候选图片不得进入 `outputs/`。
8. 不得编造图片、用户说明和正式资料均不能证明的功能或参数。
9. 产品结构、颜色、配件和品牌信息必须锁定；构图、机位、场景和卖点放大方式必须主动变化。
10. 所有重试都有最大次数；同一根本原因连续处理三轮仍失败时停止。

## 六、端到端状态流

任务按照以下状态推进：

1. `intake_pending`：需求待分流；
2. `assets_archived`：产品素材、授权和哈希已归档；
3. `selling_points_draft`：卖点待检查；
4. `selling_points_confirmed`：用户已确认最终卖点；
5. `prompts_draft`：首图和详情页提示词待检查；
6. `prompts_confirmed`：用户已确认并锁定整套提示词；
7. `style_anchor_pending`：等待生成和确认按范围确定的风格锚点；
8. `generating`：按编号连续生图并逐张验收；
9. `single_images_passed`：全部单图已通过；
10. `set_review_pending`：等待整套一致性验收；
11. `user_acceptance_pending`：等待用户最终验收；
12. `approved`：用户已验收；
13. `promoted`：正式成果已非覆盖晋级到 `outputs/`。

状态只能按门禁推进。任务中断时，从第一个未通过的图片编号继续。

## 七、任务档案与编号

每项任务在 `temp/taobao-jobs/<job-id>/` 建立独立档案，至少包含：

- 产品原图、参考素材及其哈希；
- 素材上传授权记录；
- 最终卖点表及证据来源；
- 首图设计卡片与纯净提示词；
- 详情页设计卡片与纯净提示词；
- 候选图片及下载来源；
- 每张图片的验收记录；
- 整套一致性验收记录；
- 用户确认记录；
- 正式晋级记录。

### 7.1 编号

- 卖点：`S01`、`S02`、`S03`；
- 首图：`H01`、`H02`、`H03`；
- 详情页：`D01`、`D02`、`D03`；
- 版本：`V1`、`V2`、`V3`。

同一张图的提示词、候选图片和验收记录使用相同编号，例如 `H03-V2`。

### 7.2 非覆盖版本

任何修改都创建新版本，旧版本保留。用户给出明确修改意见后，直接创建新版本并执行，不重复确认同一修改方案。

### 7.3 数组项目与提示词映射契约

JSON 模板中的数组保持为空；任务初始化和运行时写入项目后，门禁必须逐项校验以下字段：

- `product.assets` 每个 item 至少包含 `id`、`path`、`sourcePath`、`fileName`、`bytes`、`sha256`、`authorizationConfirmed`、`authorizationStatement`；
- `product.facts` 每个 item 至少包含 `id`、`name`、`value`、`evidenceType`、`evidenceReference`、`verified`；
- `candidates` 每个 item 至少包含 `id`、`type`、`version`、`promptId`、`path`、`acceptancePath`、`sha256`、`bytes`、`width`、`height`、`status`、`quality`；
- `history` 每个 item 至少包含 `at`、`actor`、`action`、`itemId`、`version`、`statement`；
- `promotion.files` 每个 item 至少包含 `id`、`path`、`fileName`、`bytes`、`sha256`、`type`、`version`；
- `promptSet.items` 每个 item 使用 `claimId` 与 `roleId` 分离语义：`claimId` 只能是 `Sxx` 或空值，`roleId` 只能是 `R01`、`R02` 等或空值；淘宝首图组（首页图）通常使用 `claimId`，详情角色页可使用 `roleId`。
- `promptSet.styleLock` 固定字段为 `brand`、`productColor`、`productStructure`、`productMaterial`、`productProportion`、`productAccessories`、`corePalette`、`typography`、`informationHierarchy`、`lighting`、`photographyStyle`、`forbiddenContent`；模板默认空对象，进入提示词确认前完整写入。

`generation.styleAnchor.itemId` 在 JSON 模板中默认空，由任务初始化按范围设为 `home/full=H01` 或 `detail=D01`。缺少任一必需字段时停止，不得依靠后续步骤猜测补全。

## 八、素材与事实管理

### 8.1 素材归档

Codex 对话中的产品图片先归档到任务目录，并记录文件名、字节数和 SHA-256。未经授权不得上传私人素材到 ChatGPT 网页。

默认通过“文件本体复制粘贴”上传到 QQ 浏览器，不向网页输入本地路径，不把 Windows 原生文件选择窗口作为默认方式。

### 8.2 卖点证据等级

`sellingPoints.items.evidenceType` 仅允许以下三种：

1. `image_visible`：图片中能够直接确认；
2. `user_confirmed`：由用户明确提供；
3. `document_proven`：由正式产品资料证明。

unsupported 只允许作为独立证据缺口状态或描述，不得写入 `sellingPoints.items.evidenceType`，也不得进入提示词或图片。

参考图、竞品图和行业案例只能作为视觉或行业启发，不得作为本产品事实证据。

## 九、卖点提炼模块

### 9.1 输入

- 产品图片；
- 用户明确提供的产品事实；
- 可选的正式产品资料。

### 9.2 硬要求

- 不直接生图；
- 不输出复杂分析；
- 不编造图片和资料无法证明的功能；
- 以 5–8 个适合淘宝的卖点为目标；
- 每个卖点配置适合上图的短标题；
- 区分适合淘宝首图和适合详情页的卖点；
- 输出简单、清楚，并附证据来源。

证据不足 5 项时，只输出已验证项和独立证据缺口，禁止用 `unsupported` 项凑数，暂停最终确认与提示词生成并等待补充资料。只有记录用户明确批准少于5项的例外，才能继续。

### 9.3 确认门禁

用户补充缺失卖点后，只修订相关部分，再输出完整编号清单。只有用户确认最终卖点后，才进入提示词规划。

## 十、淘宝首图提示词模块

### 10.1 固定原文合同

淘宝首图提示词生成只允许逐字使用 `templates/TAOBAO_HOME_IMAGE_PROMPT.md`，版本固定为 `emperor-fixed-v1`。该文件是用户批准的唯一原文，不在设计文档中建立第二份可编辑副本；任何自动改写、删减、扩展或替换均视为合同失效。

每次调用前核对 `templates/TAOBAO_HOME_IMAGE_PROMPT.lock.json` 中的规范化 UTF-8 SHA-256。版本、路径、不可变标记或指纹任一不一致时停止，不得生成首图提示词。

### 10.2 外围门禁分层

产品真实性、结构指纹、可见视角、证据边界、逐图参考绑定和成图验收继续由 Workflow、任务清单与运行门禁负责，不得把这些执行规则追加到用户固定原文中。固定原文负责生成首图提示词，外围门禁负责判断其是否可进入生图环节。

## 十一、淘宝详情页提示词模块

### 11.1 固定原文合同

淘宝详情页提示词生成只允许逐字使用 `templates/TAOBAO_DETAIL_IMAGE_PROMPT.md`，版本固定为 `emperor-fixed-detail-v1`。该文件是用户批准的唯一原文，不在设计文档中建立第二份可编辑副本；任何自动改写、删减、扩展或替换均视为合同失效。

每次调用前核对 `templates/TAOBAO_DETAIL_IMAGE_PROMPT.lock.json` 中的规范化 UTF-8 SHA-256。版本、路径、不可变标记或指纹任一不一致时停止，不得生成详情页提示词。

### 11.2 外围饱和度与真实性门禁

固定原文负责生成8–12张详情页提示词；外围门禁继续负责产品真实性、证据边界、四层完整性、内容密度、产品结构、可见视角、逐图参考绑定和成图验收，不得把这些执行规则追加到用户固定原文中。

每屏验收仍要求产品主体、使用场景、卖点证明和文字信息四层完整；1080×2340画布组织3–5个衔接区段，有效内容覆盖目标为75%–90%，连续大空白不超过画布高度15%，并至少采用两种饱满手段。证据不足时不得虚构收纳、安装、清洁、参数或其他产品能力；只输出可证明内容和证据缺口，等待补充资料。只有记录用户批准少于8屏的例外时，才可继续不足8屏的方案。

## 十二、提示词锁定

用户确认整套提示词后，锁定：

- 品牌和产品名称；
- 卖点、证据与编号；
- 主标题、副标题和标签；
- 图片顺序；
- 产品颜色、结构和配件；
- 图片比例与尺寸；
- 整套视觉风格；
- 禁用内容。

锁定后不得静默换词、增加功能或调整卖点顺序。每张图同时保存设计卡片和纯净生图提示词；实际提交时只复制纯净生图提示词。

## 十三、网页生图流程

1. 只在首个实际队列项前打开一次 QQ 浏览器中的 ChatGPT 干净新对话，记录整套唯一会话引用和新建次数1；
2. 运行上传前门禁，确认授权、文件、哈希和任务状态；
3. 复制产品图片文件本体并粘贴一次；
4. 确认网页出现正确产品缩略图并运行上传后门禁；
5. 由任务初始化按范围确定风格锚点：`home/full=H01`，`detail=D01`；提交该首个实际队列项的 `V1` 纯净生图提示词；
6. 下载并归档该图片，执行逐张验收；
7. 图片通过后由用户确认视觉方向，并写入整套风格锚点；
8. `home` 范围按 H02 至最后一张首图继续；`full` 范围按 H02 至最后一张首图，再在同一GPT对话窗口按 D01 至最后一张详情图；`detail` 范围按 D02 至最后一张详情图；
9. 首图切换详情页、后续图片和当前图返修均不得新建GPT对话；每张记录同一会话引用，首项动作是 `opened_new`，后续动作是 `reused_existing`；
10. 每张图下载后立即归档并验收，通过后才提交下一条；
11. 全部单图通过后执行整套一致性验收；
12. 用户最终验收后，运行正式晋级门禁。

后续正常情况下只发送提示词。每条提示词都包含产品一致性锁定要求；发现产品漂移时，当前图片重新附带原产品图生成，不继续向后扩散。

## 十四、风格锚点与统一变化

### 14.1 整套锁定

- 产品结构、颜色、材质、比例和配件；
- 品牌信息；
- 核心配色；
- 字体气质和信息层级；
- 摄影质感和光线语言；
- 卖点编号、术语和禁用内容。

### 14.2 允许变化

- 构图和镜头角度；
- 场景和道具；
- 产品摆放位置；
- 卖点局部放大形式；
- 首图冲击节奏与详情页叙事节奏；
- 每屏的信息密度。

按范围确定的首个实际队列项经用户确认后成为整套风格锚点。后续图片必须继承锁定项，但不能复制相同构图。

## 十五、质量门禁

### 15.1 逐张验收

每张图片检查：

1. 产品型号、颜色、结构、材质和配件是否与原图一致；
2. 是否只表达指定卖点；
3. 卖点是否有真实证据；
4. 文字、编号和配图是否语义对应；
5. 主标题、副标题和标签是否准确、无乱码；
6. 比例、尺寸和构图是否符合设计卡片；
7. 是否存在多余零件、结构变形、错误人体、悬浮物等 AI 异常；
8. 是否出现水印、二维码、虚构价格、乱码英文等禁用内容。

当前图片未通过时，只修改当前图片，不得发送下一条提示词。

### 15.2 整套一致性验收

全部单图通过后检查：

1. 产品型号、颜色、材质和部件始终一致；
2. 品牌、卖点名称和术语前后一致；
3. 配色、字体气质、信息层级、光线和摄影质感统一；
4. `full` 范围下，淘宝首图组（首页图）与详情页属于同一套视觉语言；`home` 或 `detail` 单一范围填“不适用及原因”，不得留空跳过；
5. 相邻图片的构图、机位和产品位置有明显变化；
6. 核心卖点没有遗漏、冲突或重复冒充；
7. `full` 范围下，淘宝首图组（首页图）提出的卖点在详情页得到进一步证明；单一范围填“不适用及原因”；
8. 详情页浏览节奏完整且顺序合理；
9. 图片数量、编号、尺寸、文件名、提示词和验收记录一一对应。

只有单图全部通过且整套一致性通过，才能请求用户最终验收。

## 十六、异常处理与停止条件

### 16.1 产品漂移

按以下顺序处理：

1. 强化产品锁定要求并重做当前图片；
2. 重新附带原产品图并重做；
3. 在原GPT对话中收紧构图要求并再次附带原图；禁止自动新建对话。

第三轮仍失败时停止，保留图片、提示词和证据并报告。

### 16.2 中文文字错误

按以下顺序处理：

1. 针对错字、漏字或乱码定向重做；
2. 生成不含错误文字的干净画面；
3. 使用准确文字排版完成兜底。

不得无限抽图。最终文字必须逐字核对。

### 16.3 上传与下载异常

- 同一素材文件本体复制粘贴失败一次即停止自动上传，不连续猜测按钮或坐标；
- 无法确认网页中的素材缩略图时禁止提交提示词；
- 无法可靠定位本次下载文件、文件正在占用或哈希变化时停止归档；
- 文件归档时禁止覆盖同名文件；
- 剪切前后必须验证哈希和字节数一致，目标存在且原位置不再存在。

### 16.4 修改范围

- 明确的局部修改：创建当前图片的新版本并连续执行、检查、复测；
- 大幅改变视觉方向：停止当前整套并等待用户决定是否从首张建立新的整套版本；
- 改变产品、品牌或任务类型：停止当前链路并建立新任务。

## 十八、测试与发布标准

### 18.1 基线测试

在正式 Skill 创建前，使用无该 Skill 的独立执行场景，记录代理是否会：

- 跳过任务分流；
- 未经确认直接生图；
- 编造产品卖点；
- 丢失提示词或错配图片；
- 跳过逐张验收；
- 只检查单图而忽略整套一致性；
- 未经用户验收写入 `outputs/`。

### 18.2 试运行测试

- 模板必填字段和状态迁移测试；
- 未确认卖点时禁止生成提示词或生图测试；
- 未确认提示词时禁止生图测试；
- 未确认首个实际队列项时禁止连续生成测试，并分别覆盖 `home`、`detail`、`full`；
- 上一张未通过时禁止下一张测试；
- 产品漂移、文字错误、上传失败和下载不确定测试；
- 未完成整套验收时禁止正式晋级测试；
- 一项真实淘宝产品完整套图；
- 至少一次明确修改与版本闭环。

### 18.3 Skill 测试

- 使用正式 Skill 重跑独立任务；
- 检查代理是否遵守证据、门禁、版本和验收规则；
- 发现新规避方式或遗漏时补充规则并复测；
- 运行 Skill 结构验证、项目回归和项目完整性自检。

### 18.4 发布条件

只有以下条件全部满足，才能升级为正式 Skill：

1. 输入、输出和任务分流边界明确；
2. 一项真实产品完整闭环通过；
3. 至少一次修改闭环通过；
4. 正常路径和主要异常路径通过；
5. 逐张与整套验收标准可执行；
6. 自动重试与停止条件已验证；
7. Skill 基线、复测和结构校验通过；
8. 关键规则写入 `DECISIONS.md`；
9. 发布变更写入 `CHANGELOG.md`；
10. 项目完整性自检通过。

## 十九、验收标准

- 需求能够正确分流；
- 产品事实和卖点都有可追踪证据；
- 首图和详情页提示词均可独立保存并直接提交；
- 提示词、图片、版本和验收记录一一对应；
- 产品在整套图片中保持一致；
- 风格统一但构图和页面节奏具有变化；
- 中文文字准确，无水印、二维码、虚构价格和乱码；
- 中断后能够从第一个未通过编号继续；
- 候选与正式成果严格分离；
- 未经用户验收无法正式晋级。

## 二十、客观边界

- ChatGPT 网页和生图结果属于外部服务，界面和输出稳定性可能变化；
- 产品图片无法证明的性能和参数必须由用户或正式资料提供；
- AI 生图可能出现产品漂移和中文文字错误，因此逐张验收和排版兜底不可省略；
- 首版不使用付费 API，不对外发布，不修改账号与权限；
- 当前设计完成不等于正式 Skill 已发布，必须先完成试运行和验证。
